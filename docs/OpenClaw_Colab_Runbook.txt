# OpenClaw + Colab Runbook

Este ficheiro documenta a forma correta de arrancar a demo NPC Society com OpenClaw, Unity, Colab, Cloudflare Tunnel e proxy local.

Objetivo:
- Evitar depender de memoria ou instrucoes incompletas.
- Reproduzir a demo funcional depois de o Colab reiniciar.
- Garantir que o OpenClaw consegue chegar ao Ollama atraves de http://127.0.0.1:11434.

Modelo validado:
qwen3:4b-instruct

Nao instalar qwen2.5 apenas porque apareceu em algum log antigo/default. O projeto foi validado com qwen3:4b-instruct.

Cadeia correta:
Unity
-> Flask Bridge local: http://127.0.0.1:5055
-> OpenClaw Gateway local: http://127.0.0.1:18789
-> Proxy local no PC: http://127.0.0.1:11434
-> Cloudflare Tunnel
-> Ollama no Colab
-> qwen3:4b-instruct

Importante:
127.0.0.1 no Colab nao e o mesmo 127.0.0.1 do PC.
O OpenClaw corre no PC, por isso precisa de encontrar algo em http://127.0.0.1:11434 no PC.
Esse "algo" deve ser o proxy local que encaminha para o URL Cloudflare do Colab.

5. Colab - criar Cloudflare Tunnel
============================================================

Executar no Colab:

%%bash
set +e

pkill -9 -f cloudflared || true
sleep 2

rm -f cloudflared.log

nohup ./cloudflared tunnel \
    --url http://127.0.0.1:11434 \
    --no-autoupdate \
    > cloudflared.log 2>&1 &

echo "Waiting for Cloudflare tunnel URL..."

for i in $(seq 1 30); do
    URL=$(grep -Eo 'https://[-a-zA-Z0-9]+\.trycloudflare\.com' cloudflared.log | head -n 1)
    if [ -n "$URL" ]; then
        echo "CLOUDFLARE_URL=$URL"
        exit 0
    fi
    sleep 1
done

echo "No URL found yet."
cat cloudflared.log
exit 1

Copiar o URL gerado.
Exemplo:
https://mental-cdna-judy-rate.trycloudflare.com

A celula terminar depois de mostrar CLOUDFLARE_URL e normal. O processo cloudflared fica em background.

Confirmar processos no Colab:

%%bash
echo "=== cloudflared process ==="
pgrep -af cloudflared || echo "cloudflared not running"

echo ""
echo "=== ollama process ==="
pgrep -af ollama || echo "ollama not running"

echo ""
echo "=== local Ollama tags ==="

============================================================
15. Explicacao tecnica para apresentacao
============================================================

A simulacao tem quatro NPCs autonomos, cada um com identidade, memoria e relacoes proprias.
O manager nao decide o conteudo da acao. Apenas controla ordem, cooldowns, limites e evita pedidos concorrentes.
Cada NPC chama o seu agente OpenClaw, recebe uma decisao do LLM e a Unity executa essa decisao.
A memoria e as relacoes sao persistidas em ficheiros JSON.
Os pedidos ao LLM sao serializados por estabilidade, para evitar timeouts e sobrecarga do backend.
